# TUI-only Decommission Plan

## Status

Proposed implementation contract.  This document is the review point before
removing retired code.  It does not alter published releases, released wheels,
tags, or their release manifests.

## Product charter

The supported product is a local-first, human-only Codex TUI workflow:

```text
TUI root
  -> reviewer child
  -> schema-validated findings in the local ledger
  -> proposer child
  -> schema-validated proposal draft
  -> proposal-assessor child
  -> human-only v6 proposal in the local ledger
```

The local `nlp-refinement` CLI owns artifact scanning, snapshot checks,
contract validation, SQLite StateStore operations, controlled handoffs, resume
queries, and proposal persistence.  The Plugin distributes the namespaced
`$nlp-review-propose` Skill and the setup Skill.

## Retired scope

The next unreleased version must not ship or advertise:

- M4 disposable repair-feasibility DOE code, fixtures, tests, or documents;
- M8 external-host coordination, local Codex app-server clients, host executor,
  host CLI, host DOE scripts, or host receipts;
- the `nlp-refinement-host`, `nlp-refinement-doe-prune`, and
  `host-execution-request` public commands;
- duplicated phase prompt files whose behavior is generated by
  `tui-child-contract` and `tui-child-bootstrap`.

Retirement does not mean that a child has a host-enforced role identity or an
independent OS sandbox.  The supported claim remains three independent generic
child contexts receiving controlled, role-specific contracts.

## Explicit non-goals

- Do not change target artifacts, automatically apply proposals, start a
  controller, app-server, daemon, or MCP bridge.
- Do not rewrite the published `v0.11.0` tag, wheel, GitHub Release, PyPI
  distribution, or its v2 release manifest.
- Do not remove v5 review protocol, v5 proposal compatibility, inventory v1,
  M0 protocol files, or historical release records in this change.  Their
  compatibility policy is a later decision.
- Do not claim native child role binding, child thread/cwd observability, or
  per-child sandbox isolation without host evidence.

## Boundaries and migration policy

| Boundary | Owner | Invariant | Violation evidence | Rollback |
| --- | --- | --- | --- | --- |
| Public CLI | `pyproject.toml`, `refine.py` | The next package publishes only `nlp-refinement`; its help has no retired host command. | Package metadata or CLI help exposes a retired command. | Revert this feature branch before release. |
| Runtime bootstrap | bootstrap/release scripts | New release records use a new schema whose command list is exactly `nlp-refinement`. v2 retains its historical three-command meaning. | A v3 record accepts legacy commands, or v2 semantics are changed. | Do not publish the new record; retain published v2 assets. |
| TUI workflow | `tui_workflow.py`, Skill, adapters | reviewer -> verified findings -> proposer -> validated draft -> assessor -> human-only v6 proposal; no target write. | Missing gate, invalid handoff, target write, or final artifact without assessment. | Stop the run; ledger remains the recovery source. |
| Existing ledger | `state_store.py`, retention paths | Historical M8 ledger records are readable for status/retention or are explicitly documented as 0.11-only before their support is removed. | Parser/retention raises for an existing M8 record. | Restore only the minimal compatibility reader; do not revive execution. |
| Released assets | Git tags/releases/PyPI | Existing 0.11.0 bytes and manifests remain immutable evidence. | Attempt to overwrite/delete published asset. | Stop; no mutation is permitted. |

## Release-manifest versioning

The retired commands are part of the semantic meaning of
`nlp-refinement-runtime-release/v2`.  The next release uses
`nlp-refinement-runtime-release/v3` with exactly one required command:

```json
{"commands":["nlp-refinement"]}
```

The v3 wheel, manifest, bootstrap configuration, tag, GitHub Release, and
PyPI upload must be created together in a separately authorized release step.
This feature branch may implement and test v3 serialization/validation, but it
must not pretend that the existing 0.11.0 v2 manifest describes the new source.

## Acceptance map

| Requirement | Evidence |
| --- | --- |
| Only one published CLI command | Package-metadata unit test and built-wheel inspection. |
| No retired runtime surface | `nlp-refinement --help` test and source/package exclusion test. |
| Bootstrap preserves historical v2 meaning and emits v3 | Focused bootstrap/release-preparer tests. |
| TUI happy path stays supported | Existing isolated reviewer -> proposer -> assessor workflow tests plus the documented real-TUI acceptance receipt. |
| Resume depends on ledger and verified handoff | Existing fresh-root resume tests. |
| No target write | Existing human-only/no-target-write tests and manual TUI acceptance receipt. |
| Old ledger safety | A fixture containing a historical M8 receipt can be queried and retained/purged safely, or an explicit 0.11-only migration document blocks deletion until this is added. |

## Implementation order

1. Add the red tests for the single public command, v3 manifest semantics, and
   absent retired runtime surface.
2. Cut the packaging and CLI public surface.
3. Remove the M4/M8 code, scripts, tests, docs, and generated-obsolete prompt
   artifacts after each removal has no remaining static reference.
4. Rewrite README, AGENTS.md, setup Skill, Plugin metadata, and acceptance
   documentation around the supported TUI workflow.
5. Run focused tests, the complete test suite, the contract validator, a
   build-and-inspect wheel check, and strict change review.
6. Present the uncommitted diff and evidence.  Commit, merge, tag, publish,
   install, and release uploads each require separate user authorization.

## Deferred compatibility decision

Before removing v5 proposal support, inventory v1, M0 artifacts, or old
release manifests, record for each item: current reader, persisted-record
shape, historical fixture, explicit migration/read-only policy, and retention
behavior.  Candidate count from a scanner is not deletion evidence.
